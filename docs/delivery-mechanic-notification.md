| 項目 | 設定 |
|---|---|
| 対象 | 納車後アンケートの `納車全体の印象` が🔴ネガティブ、または🟡ややネガティブ |

| メンション | `@channel`（Slack API形式は `<!channel>`）。支社・サポートチームのユーザーグループメンションは追加しない |
| 本文 | 既存通知と同じアンケート本文・顧客照合情報を使用 |

| 判定元 | 既存の `evaluateBaseSatisfaction` の結果を再利用。再判定・BigQueryの再照合はしない |
| 追加しない通知 | 🟢、満足度未回答、DIRECT評価だけの低評価、自由記述だけの回答、紹介意向だけの低評価 |
| 過去の回答 | 遡って送信しない。有効化後に新しく処理されたフォーム回答のみ |

判定に使う3問は次のとおり。いずれかに「不満がある」があれば🔴、「やや期待と異なっていた」が2問以上で🔴、1問で🟡となる。

1. 納車されたお車の状態に、ご満足いただけましたか？
2. 納車当日の対応（ご説明、書類のお渡し、お車の受け渡し時間など）は、スムーズでしたか？
3. ご契約から納車までの全体の流れについて、ご満足いただけましたか？

既存GASに小さな追加処理を置き、専用Webhookに送信する構成。別のBot・実行環境・トリガーを増やさず、元の通知処理と判定を共有する。追加側は既存通知処理の後に実行し、追加側の通信失敗を呼び出し元に伝播させない。

## 有効化手順

1. SlackのIncoming Webhook設定で、上記の追加通知先専用のWebhookを作成する。投稿名は `納車後アンケート｜整備確認`。設定ID・設定画面URL・投稿先・登録者・有効状態を記録する。既存Webhookは変更しない。
2. 本番の最新コードがバックアップと一致するか再確認し、同時編集がないことを確認する。差分があれば全体の上書きはせず、1行の追加を現行コードに適用する。
3. 新しい `MechanicNotification.gs` を追加して保存した後、既存 `コード.gs` の追加呼び出しを保存する。新規ファイルを先に保存することで未定義関数の呼び出しを防ぐ。
4. GASのスクリプトプロパティ `SLACK_MECHANIC_WEBHOOK_URL` に新しいWebhook URLを設定する。既存の `SLACK_WEBHOOK_URL` は維持する。追加プロパティの設定を最後に行い、それまでは追加通知を停止状態に保つ。
5. 保存後にコードと設定を読み戻して照合する。既存の `onFormSubmit` / フォーム送信時 / `Head` トリガーを使用し、新しいトリガーやデプロイは作らない。
6. `testDeliveryMechanicNotification` を手動で1回実行する。整備士チャンネルだけに「動作確認・テスト」「対応は不要です」と明記した架空メッセージをメンションなしで送る。フォーム送信・BigQuery照合・既存チャンネルへの送信は行わない。
7. GAS実行ログとSlackへの到達・テストにメンションがないことを確認し、実施日と結果をこの資料へ追記する。テスト用関数はトリガーに登録しない。

`SLACK_MECHANIC_WEBHOOK_URL` の値をソースやGitHub、ログへ記録しない。追加コードは元のURLと同じ値・不正なURLを拒否するが、別URLが同じチャンネルを指すことは検知できないため、Slack画面で投稿先を確認する。

現在の既存連携に合わせたLegacy Incoming Webhookを使用。Slackはこれを旧式と案内しているため、将来のSlack側移行時には既存通知と合わせてSlack App方式への移行を検討する。新たな旧式連携の作成が許可されない場合も、同じGAS側のプロパティ構成でSlack AppのIncoming Webhookを使用できる。

## 停止・復旧

- 追加通知だけを停止する場合：`SLACK_MECHANIC_WEBHOOK_URL` を削除、または空にする。既存通知先の設定は維持する。
- Webhookを作り直す場合：追加通知先を確認して再発行し、このプロパティだけを差し替える。手動テストで到達を確認する。
- コードを戻す場合：まず追加プロパティを削除し、`コード.gs` の追加呼び出し1行を削除する。その後に新規ファイルを削除する。後続の変更がある場合は古いファイル全体を上書きしない。
- Googleアカウントの廃止・変更時：既存のフォーム送信トリガーも含め、後任の管理アカウントで必要な権限とトリガーを再設定する。[引き継ぎ資料](slack-incoming-webhooks.md)も参照。

追加通知は自動再送しない。追加側だけ失敗しても既存通知は再送せず、`[delivery_mechanic_notification]` のログに結果を残す。失敗を捕捉するため追加側の失敗だけではGASのトリガー失敗メールは届かない。必要時は既存通知・元の回答と照合して未着を補う。GAS全体の実行時間上限やサービス障害を完全に隔離する構成ではない。
